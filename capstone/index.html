A HIPAA compliance pipeline

I built a deployment pipeline that will not ship a patient-intake application unless it meets HIPAA Security Rule safeguards, and that leaves signed, tamper-evident evidence an assessor can verify without trusting me.

Why HIPAA comes first

The application stores patient intake records, so protected health information is in scope and HIPAA is mandatory the day the system goes live. SOC 2 and CMMC were deprioritized because they are driven by customer or contract opportunity, not by the data itself. I chose the obligation over the opportunities, and every policy and OSCAL requirement in the repository cites a 164.x control.

The scope stays honest about what code can prove. This build implements the Technical Safeguards (164.312) and the data backup requirement in 164.308(a)(7)(ii)(A). Physical Safeguards are inherited from AWS under the shared responsibility model and are not claimed. The OSCAL component cites NIST SP 800-66 Rev. 2 as its catalog source, because there is no official OSCAL catalog for HIPAA itself.

The pipeline

Every push runs five named steps in order. Apply runs only on main, and only with zero policy failures.

  1. PlanTerraform plan against remote state, saved as text and JSON.
  2. Policy checkConftest evaluates five HIPAA Rego policies against the plan.
  3. ApplyMain branch only, zero failures only, under a dedicated apply role.
  4. SignEvidence bundled, hashed with SHA-256, and signed with Cosign keyless signing.
  5. UploadBundle, hash, signature, and receipt land in an S3 Object Lock vault.

The job fails last, after evidence is stored. A blocked change leaves the same signed record as an approved one.

What I built

Four enforced layers, then a fifth that keeps watching.

  1. Infrastructure as code (Terraform)A customer-managed KMS key with rotation, encrypted S3 and DynamoDB, CloudTrail with log file validation, and remote state.
  2. Policy as code (Rego with Conftest)Five HIPAA policies evaluated against every Terraform plan, covered by 26 unit tests.
  3. CI/CD gate (GitHub Actions with OIDC)Separate plan and apply roles. Pull requests run read-only with no ability to decrypt PHI; only main can apply.
  4. Compliance documentation (OSCAL with compliance-trestle)A validated component definition and profile, with each control linked to the evidence that proves it.
  5. Continuous monitoringAWS Config managed rules on a scoped recorder, EventBridge alerts on out-of-band changes, a nightly drift check under a read-only role, and 11 live control tests whose results go inside each signed evidence bundle.

Using the second attempt for what it's for

The CGE-P allows a second attempt within 30 days. With the certificate already earned, I used that window to act on reviewer feedback, reproducing each finding before changing anything. The reviewer was pointing at the distinction auditors draw between design and operating effectiveness: a compliant plan shows design, while live tests inside a signed bundle show the controls actually work.

Known trade-offs

Documented in the repository, not hidden, each with a planned fix.

State bucket outside the gate

Terraform can't keep its state in a bucket that doesn't exist yet, so the state bucket was bootstrapped by hand. It is versioned, private, TLS-only, and watched by AWS Config, but outside the Rego suite. Next: a small bootstrap configuration with its own policy run.

Inline role policies and AWS Config

AWS Config's managed IAM rules evaluate customer-managed policies, not inline ones. That control relies on the live IAM simulation and an alert. Next: a custom Config rule.

API authentication is partial

HIPAA 164.312(d) stays marked partial until the intake API requires authentication. Next: an authenticated intake API, then reassess the claim.

Apply role breadth

The deploy role could be scoped more tightly. Next: narrow it to the resource types the stack actually manages.

Where it started

The capstone builds on an earlier lab in the same program: a reusable Terraform module that deploys a compliant S3 bucket with a dedicated, encrypted access-log bucket and enforces NIST SP 800-53 controls at deploy time, with plan and state evidence committed alongside the code. View the lab on GitHub.

The platform came first. An older Mac couldn't run current tooling, and Windows with WSL doubled the troubleshooting surface, so I revived an older ThinkPad with a new battery and a 1TB drive and ran Linux Mint, which shares an OS base with GitHub's Ubuntu runner. Local results predict CI results, and the one place they didn't (default file permissions) became the false-drift fix above.

Built with: Linux Mint, Bash, Terraform, AWS (KMS, S3 Object Lock, DynamoDB, Lambda, CloudTrail, Config, EventBridge, IAM with GitHub OIDC), Open Policy Agent (Rego) and Conftest, GitHub Actions, Cosign and Sigstore, compliance-trestle (OSCAL), semgrep, and jq.
